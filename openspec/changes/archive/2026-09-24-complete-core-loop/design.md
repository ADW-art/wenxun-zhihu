## Context

当前页面和 API 已覆盖文字巡查、分析、整改和复核，但证据仍只有描述文本。数据模型已经包含 InspectionEvidence 和 TaskEvidence，可直接扩展文件存储，不需要新增数据库迁移。

## Goals / Non-Goals

**Goals:**

- 使用统一存储接口处理巡查和整改文件。
- 本地开发使用文件系统，后续生产可替换 S3 兼容实现。
- 图片统一转为 WebP 并移除 EXIF。
- 提供安全的文件读取和 Markdown 报告下载。

**Non-Goals:**

- 不实现恶意文件病毒扫描。
- 不实现对象存储签名 URL。
- 不实现在线 Office 文档预览。
- 不生成 PDF，最终 PDF 转换留到提交阶段。

## Decisions

### 文件存储抽象

- 选择：`FileStorage` 接口加本地实现。
- 原因：业务层不依赖磁盘路径，后续只需实现 S3 Provider。
- 备选：页面直接调用 `writeFile`。拒绝，因为无法安全替换和测试。

### Sharp 图片处理

- 选择：图片转为 WebP，质量 88，并执行自动旋转。
- 原因：统一格式、减小体积、移除 EXIF，同时保留正常观感。
- 备选：原图存储后单独清理 EXIF。拒绝，因为依赖更多元数据处理步骤。

### 路径安全

- 选择：读取时解析绝对路径并校验仍位于存储根目录内。
- 原因：阻止 `..` 路径穿越。
- 备选：只过滤字符串。拒绝，因为 Windows 路径形式复杂。

### 报告格式

- 选择：首版导出 Markdown，浏览器可直接阅读并便于后续转 PDF。
- 原因：实现可靠、内容可审阅、无额外排版依赖。
- 备选：服务端直接生成 PDF。暂缓，因为正式提交报告应使用赛事模板。

## Risks / Trade-offs

- [本地文件在无状态部署中丢失] → 生产阶段切换 S3 兼容实现。
- [图片转换失败] → 返回校验错误，保留原表单内容并允许重试。
- [文件访问绕过权限] → 文件接口只依赖不可猜测 UUID，后续 S3 阶段加入签名 URL。
- [报告内容过长] → Markdown 下载不受页面布局影响，正式 PDF 阶段再做分页。

## Migration Plan

新增文件不需要数据库迁移。部署时确保 `uploads/` 挂载持久卷；切换 S3 时只需要实现同一存储接口并更新环境变量。
